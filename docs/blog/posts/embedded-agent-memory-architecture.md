## 问题从哪里开始

谈起 Agent 长期记忆，最常见的架构图长得很像：`Qdrant` 或 `Milvus` 存向量，`Neo4j` 存知识图谱，旁边挂一个 Python 服务跑 `PyTorch` 和 `LangGraph` 做抽取与召回。在云端 Demo 里这套组合跑得很顺手，但一旦把 Agent 搬到内存吃紧的边缘端侧，或者接入实时语音对话，很快就会撞上三堵硬墙。

第一堵墙是资源与部署。嵌入式设备装不下几百兆的 Python 运行时和动辄数 GB 的内存峰值，每多拉起一个常驻子进程，冷启动时间和 OOM 风险都在往上飙。

第二堵墙是延迟。语音全双工对话里，首字响应本身按几十到几百毫秒算账；如果每次用户开口前，记忆模块还要跨进程 RPC、调远端 Embedding 或跑一轮重型模型推理，整条交互链路立刻变卡。

第三堵墙最容易在前期被低估，叫**过度个性化误注入（Over-Personalization）**。很多人做检索评测只盯着 `Recall@10` 调参数，结果线上跑起来发现，用户明明只是随口问“怎么安慰一个最近压力大的朋友”，记忆模块因为撞上了“朋友”“压力”“放松”几个词，把用户半年前自己打游戏解压的旧事塞进了上下文，大模型顺手就把回答拐偏了。真实交互里，胡乱翻旧账比偶尔没想起来更让人出戏。

最近我把一套端侧长期记忆引擎完整重做了一遍：不引入外部数据库服务，不依赖 Python 运行时，所有权威状态落在单个 SQLite 文件里，检索、双时态知识图谱、向量聚类画像和静态多语种 Embedding 全跑在同一个 Rust 进程内。满库 2000 条笔记时，单轮检索延迟在桌面上是百微秒级（弱算力端侧约 1–2 ms），模型与词表部署总大小压到 137 MB，同时在 LoCoMo、LongMemEval、OP-Bench 和 Memora Weekly 四套公开基准上做了一轮完整对照。

这篇文章把整套系统的四个核心切面拆开讲清楚：双时态知识图谱怎么建才不会变成噪声网、向量聚类怎么把几百条碎片压缩进 2000 字常驻画像、四信号混合召回如何压低无关误注入，以及端侧部署时踩到的几个非常隐蔽的内存与分词坑。

## 一、整体骨架：单文件权威存储，内存重建多视图索引

对于面向个人或家庭成员的长期记忆，在有自然遗忘和容量上限的前提下，活跃笔记规模通常在几百到几千条这个量级。在这个规模下，强上分布式向量库属于典型的架构过载。

更务实的做法是把 SQLite 当成唯一的持久化真相源，启动时把活跃笔记、向量 BLOB、图谱边和时间线链表一次性加载进内存，构建轻量级倒排、连续向量空间和邻接表：

```text
                       ┌─────────────────────────────────────────────┐
                       │             单文件 SQLite 权威存储            │
                       │  notes · vectors(BLOB) · graph_nodes/edges  │
                       │  timeline_events · persons · profile_cache  │
                       └──────────────────────┬──────────────────────┘
                                              │ 启动加载 / 写入同事务落盘
                                              ▼
┌──────────────────────┐    ┌─────────────────────────────────────────┐
│    写入与巩固通道      │───►│           进程内多视图索引               │
│ · 显式记住 / 修改 / 忘 │    │ · BM25 倒排 + 紧凑 u32 中文双字倒排      │
│ · 空闲增量抽取与槽位覆写│    │ · 连续内存向量空间（按 model_id 隔离）  │
│ · 同事务关闭旧图谱边   │    │ · 双时态知识图谱（邻接表 + 活跃出度）     │
└──────────────────────┘    │ · 按人串联的事件时间线链表               │
                            └──────────────┬──────────────┬───────────┘
                                           │              │
                  ┌────────────────────────┘              └───────────────────────┐
                  ▼                                                               ▼
┌──────────────────────────────────┐                          ┌──────────────────────────────────┐
│  常驻背景（System Prompt，2000字） │                          │   按需召回与主动检索               │
│ · 安全域隔离凝聚聚类压缩           │                          │ · 自动注入：5道门控 + MMR，≤3条/500字│
│ · 软配额分配 + 可查询目录          │                          │ · 显式搜索：四信号分数感知 RRF，≤32条│
│ · 按会话修订号冻结，保前缀缓存     │                          │ · 图谱子图 / 时间线 / 原始会话 FTS  │
└──────────────────────────────────┘                          └──────────────────────────────────┘
```

数据层先把记忆分成三种形态：`Semantic` 存带固定槽位键（`memory_key`，比如 `health.allergy`、`preference.coffee`）的长期事实；`Episodic` 存带发生时间和地点锚点的情景经历；`Reflective` 存智能体自己总结的行为教训。

很多记忆系统的脏数据源自写入阶段只增不改，在写入层维护槽位键可以直接消除这类冲突。一旦 `Semantic` 事实按 `(person_id, subject, memory_key)` 归槽，新事实写入时就能在同一事务里把同槽位旧记录标记为失效，顺手关闭对应的图谱边并移除旧向量。在 Memora Weekly 的遗忘测试（Track B lifecycle）里，仅靠这套同事务联动失效机制，已遗忘事实的 `Forget Absence@10` 就能做到 `98.63%`，而只堆叠原始对话不维护生命周期的基线只有 `8.22%`。

## 二、双时态知识图谱：轻量投影、Hub 抑制与加权 PPR

给个人记忆加知识图谱，最容易掉进的坑是照搬学术界的大图思路：每条对话先跑两轮 OpenIE 抽一大堆自由文本三元组，然后直接跑标准 PageRank。结果通常很惨：抽取成本高、实体碎片化严重，而且图谱跑两跳之后把半个库的无关记忆全拉出来了。

我们的图谱设计走了另一条路：**以规则投影为底座、可选三元组做增强，用双时态控制失效，用受限加权 PPR 做两跳扩散。**

### 1. 怎么把一条笔记投影成图

每条活跃笔记写入时，都会确定性地投影成若干 `GraphNode` 和 `GraphEdge`，边上同时记录 `valid_from`（事实生效时间）、`invalid_at`（被覆盖或遗忘时间）和 `recorded_at`（入库时间）。边的权重按可靠程度分三档，统一乘以笔记显著度 `salience = clamp(importance / 10.0, 0.2, 1.0)`：

| 边类型 | 来源 | 边权系数 | 作用 |
| --- | --- | ---: | --- |
| 显式关系边 | 巩固模型抽出的 `(source, relation, target)` 三元组 | `1.0 × salience` | 承载最强的语义关联（如 `likes_food`、`friend`） |
| 主事实 / 地点 / 主题边 | 锚点主体指向显式 `entities`、地点 `district` 或回退规则实体 | `0.85 × salience` | 没抽三元组时保证基本连通性 |
| 共现边（`co_occurs`） | 同条笔记内 2–5 个实体的两两直连 | `0.35 × salience` | 绕开“用户”超级节点，实现实体到实体的直接两跳 |

如果笔记没有模型标注的实体或三元组，本地规则提取器会从深层槽位名、引号短语、常见地名/机构后缀和英文专名里做确定性补全，不需要额外调 LLM。同时，节点主键做跨类型归一：`Pet`、`Place`、`Preference` 和普通 `Entity` 共用同一实体空间，后续有更具体类型进来时自动升级，不会因为一次标成 `Entity`、另一次标成 `Pet` 就裂成两个节点。

### 2. 上手就会踩的三个图谱细节

实际把图谱接进混合检索后，有三个非常具体的 bug 让我调了很久。

**第一个是 Hub 节点广播灾难。** 个人记忆图谱是典型的星型结构，几乎所有事实都挂在“用户”这个锚点节点上。如果在 PPR 里允许质量流经“用户”或高频通用词节点，两跳扩散瞬间就退化成全库随机抽样。解决办法很直接：种子匹配和游走扩散同时跳过 `Topic` 节点、泛指词，以及活跃出度超过阈值的 Hub 节点；并且对种子笔记自身产生的回流乘以 `0.25` 的衰减，避免图谱只把已经命中的旧笔记又推高一遍，真正把分留给第二跳的新证据。

**第二个是短实体误匹配与第三方人物断裂。** 早期种子实体匹配图省事写了 `normalized_query.contains(node_name)`，结果英文笔记里如果抽出了 `"ai"`、`"cat"`、`"art"` 这种短实体，查询里出现 `"said"`、`"vacation"`、`"start"` 就会被子串误触发。后来统一抽了 `query_matches_node_name`，对首尾都是 ASCII 字母数字的节点名强制检查左右非字母数字词边界，中文则保持正常子串命中。

另一个隐藏更深的 bug 出在多用户命名空间上。为了隔离家庭成员，我们给 `NodeType::Person` 节点的哈希键加了 `person_id`。最初写投影时顺手把三元组里所有 `Person` 节点都绑上了当前笔记的 `note.person_id`（比如 `"owner"`）。这导致一个荒唐的结果：笔记 A 写“用户认识了朋友周明远”，笔记 B 写“周明远养了一只柯基”，因为“周明远”在不同路径里被分别散列成了带 `"owner"` 的人节点和不带 `person_id` 的实体节点，两跳直接断成两截。修法很简单：**只有指代当前说话人本人的 `Person`（`主人`/`我`/`owner` 或等于 `note.person_id`）才绑定命名空间，所有第三方人物跨笔记共享全局实体键。**

**第三个是边权分层后的 PPR 归一化陷阱。** 把显式边、主边、共现边分层设为 `1.0 / 0.85 / 0.35` 后，最初我的 PPR 扩散公式保留了旧写法：

```rust
// 旧写法：按活跃出度数均分，再乘边权
let spread = mass * decay / (active_count as f32);
let contrib = spread * edge.weight * edge.confidence;
```

跑完 LoCoMo 中文评测，我发现显式检索的 `@5` 和 `@10` 反而掉了零点几个百分点。拆开算一下就明白了：一条 `importance=5` 的笔记，`salience` 本来就是 `0.5`，乘上共现系数 `0.35` 后边权只剩 `0.175`；除以 `active_count` 再乘 `0.175`，单跳流出质量直接缩水超过八成，大量合法的两跳证据在软饱和后掉到了图谱准入阈值（`0.20`）下面。

改成按节点所有有效出边的总权重归一化后，问题立刻消失：

```rust
let weight_sum: f32 = edge_ids
    .iter()
    .filter_map(|edge_id| self.edges.get(edge_id))
    .filter(|edge| edge.invalid_at.is_none())
    .map(|edge| edge.weight)
    .sum();
let base = mass * decay / weight_sum;
let contrib = base * edge.weight * edge.confidence;
```

这样一来，每个节点的总流出转移概率之和严格守恒，既保住了显式关系边相对共现边将近 3 倍的权重优势，又不会因为调低噪声边权重而饿死两跳通路。

## 三、向量聚类用户画像：把碎片压进 2000 字而不丢红线

长期记忆除了“问到再查”，还需要一块每轮对话都带在 System Prompt 里的常驻画像，让 Agent 天然记得用户的身份、过敏史、生活习惯和重要关系。

这块区域的硬约束是 **2000 字上限**。最朴素的做法是按重要度和新鲜度排序，截断前 2000 字拼进去。但用上几周就会发现两个大问题：一是话题扎堆，用户连续一周聊咖啡、露营，六七条大同小异的偏好碎片很快把常驻名额吃干抹净，反而把低频但关键的禁忌或长期约定挤掉了；二是缓存抖动，如果每次回忆更新了访问时间或 HashMap 迭代顺序漂移，导致 System Prompt 里任意两行互换位置，LLM Provider 的 Prefix Cache 就会全盘失配，整段历史重新计费和 prefill。

我们用**安全域硬隔离的凝聚聚类 + 两阶段配额 + 确定性快照**来解这两件事。

### 1. 安全域隔离与防链式漂移的凝聚聚类

在拼装常驻画像之前，系统直接复用内存里已经算好的笔记向量，跑一遍自底向上的凝聚聚类，把同主题碎片合并成紧凑摘要。但这里有三条必须守住的工程红线：

1. **安全域绝不混聚**：属于 `health`（过敏、用药、病史）和 `constraint`（用户明确立下的行为红线）域的笔记强制单独隔离，不和普通偏好或闲聊碎片合簇，防止重要细节在摘要合并时被磨平。
2. **防链式漂移**：单链接聚类最常见的毛病是 A 像 B、B 像 C，最后把风马牛不相及的 A 和 C 串进同一个簇。合并候选时我们增加了一道全簇底线校验，要求新成员与簇内任意已有成员的最低余弦相似度不低于 `0.72 × min_similarity`，彻底堵死长链漂移。
3. **自适应阈值与 Medoid 代表**：不同向量空间的余弦分布完全不同。在语义模型空间（`potion-multilingual-128M`）里，同义笔记余弦通常在 `0.60` 以上，聚类阈值设 `0.56`；在离线哈希投影兜底空间里向量更稀疏，阈值降到 `0.42`。每个簇选出与簇内其他节点平均相似度最高的 **medoid** 当中心句，附属碎片做词集合 Jaccard 去重后再压缩拼接，去掉重复主语。

### 2. 两阶段配额、可查询目录与 Prefix Cache 保护

聚类压缩完之后，2000 字预算并不直接一刀切，而是分两阶段装入：第一阶段按身份角色与安全优先级分配保底软配额（置顶项与身份/健康类关键事实优先占 500 字，常规个人画像占 900 字，关系与高情绪重要经历占 600 字）；第二阶段把未用完的余额退回全局共享池，按综合优先级（`importance_weight × source_weight × freshness × sticky_boost`）继续补齐。

超出 2000 字放不下的记忆怎么办？我们在常驻块末尾用剩余字符自动生成一份 `## 可查询目录`，列出当前库里所有可查的 `subject` 与 `memory_key_prefix` 分类入口。模型扫一眼目录就知道“还有哪些档案没展开”，需要时自己调工具查，不用硬塞进常驻区。

为了保住大模型的 Prefix Cache，我们还加了两个容易被忽略的小设计：
- **确定性收尾排序**：同批巩固写入的笔记，`importance` 和 `recorded_at` 天然相等，任何排序末尾都必须拼上内容无关的 `Uuid` 比较，杜绝 HashMap rehash 引起行序翻转。
- **排除了访问时间的指纹冻结**：常驻快照按 `(session_id, model_context_revision)` 缓存，并维护一份排除 `last_accessed_at` 的 `ProfileFingerprint`。只要用户没改、删、新增关键事实，或者没触发上下文压缩，整段对话的常驻块一字不动。

## 四、四信号混合召回、误注入门控与中文双字倒排

做完存储和画像，真正决定日常对话体感的是检索。这里最容易犯的架构错误，是把**自动召回**和**显式搜索**用同一套打分和阈值糊在一起。

这两者的目标其实是反着的：
- **自动召回**在每轮用户说话前静默触发，预算只有 **3 条 / 500 字**。它的第一优先级是精准与克制：宁可不带，绝不乱插话。
- **显式搜索**由 Agent 判断背景不够时主动调工具发起，最多返回 **32 条**。它的第一优先级是高召回与证据完整，宁可多带几条让模型自己挑，也不要把关键线索漏在外面。

### 1. 自动召回：怎么把误注入从 18.66% 压到 8.85%

在刚接完本地静态向量模型时，我们的 LoCoMo 和 LongMemEval 召回率一下涨了不少，但一跑 OP-Bench（专门测 418 道无关个人化问句会不会误触发自动注入的基准），误注入率（FIR）高达 **18.66%**，LongMemEval 的无答案拒识集（`_abs`）误注入率甚至到了 **73.33%**。

我把误注入样本全拉出来逐条看了一遍，发现分词本身大多没切错，问题出在三个门控漏洞上：

第一，**泛词凑数**。原先词法准入只要命中 `>= 2` 个词组就放行，结果 `"looking for advice"`、`"people help others"` 这种全库高频泛词轻松凑够两个命中。我们在自动召回查询前先抽出一层中英文封闭类虚词、系词与情态助动词过滤，在多文档语料上叠加查询 IDF 覆盖占比和最高命中词 IDF 比例门槛，只命中高频泛词、覆盖不了核心信息量时直接拦掉。

第二，**向量绝对阈值失灵**。短文本在低维稠密空间里很容易出现“整体余弦偏高”的现象：一条无关问句和库里最像的笔记余弦可能有 `0.58`，但它和全库背景分布（比如 Top-K 尾部中位数 `bg_sim`）也有 `0.55`，根本没有显著区分度。于是我们在纯语义放行路径上加了一道**背景显著性 Margin 校验**：有共享词锚点时要求 `sem_score - bg_sim >= 0.035`，纯向量无词法锚点时要求 `>= 0.06`。同时，如果原问句包含引号、数字规格或非句首专有名词等硬限定词，纯向量通路不得在完全缺失核心限定词的情况下放行。

第三，**场景冲突与近义占坑**。在候选进入 500 字打包前，先用内存中现成的向量做一轮轻量 **MMR（最大边际相关性）** 重排，与已入选条目余弦过高时压低边际分，把 3 条名额留给多跳场景里的互补证据。用户如果正在下达即时设备控制或工具查询指令（比如站起、导航、查电量、问天气），且句中不含“记得、上次、以前”等历史词，直接拦截所有 `Episodic` 经历；同会话内一条记忆确认送达后冷却 30 秒，长篇反思教训（`> 180` 字）给 5 倍冷却和更严门槛。

四道门控叠加完之后重新跑基准，LoCoMo 和 LongMemEval 正样本召回几乎零回退（LongMemEval `Recall@10` 保持 `95.38%`），而 OP-Bench 误注入率直接从 **`18.66%` 掉到 `8.85%`**（拒识率升至 `91.15%`），LongMemEval `_abs` 误注入率从 **`73.33%` 降到 `46.67%`**。

### 2. 显式搜索：四信号分数感知 RRF 与紧凑 `u32` 中文双字倒排

显式搜索在启用语义向量空间时，使用分数感知的 RRF（`RRF_K = 45`）融合四路信号：BM25 词法（权重 `1.45` + 归一化得分与精确词组覆盖率）、语料 IDF 加权向量（`0.95`）、图谱两跳 PPR（`0.35`）以及中文双字倒排（`0.55`），最后叠加上轻量多语种时间意图重排（规则识别“昨天/上周/去年/最近一次/最早”等时间窗与序关系，把 LongMemEval 的 `temporal-reasoning` `Recall@32` 推到 `95.09%`）。

这里专门讲一下中文双字倒排的优化过程，因为我们在这个小模块上连续撞过一次内存坑和一次延迟坑。

为了避免 `jieba` 开启 HMM 后把“看猫”合成未知词导致漏查“猫”，系统关闭了 HMM。但关掉 HMM 的代价是未登录的中文人名和译名会被切碎，例如 `"梅拉妮"` 会被切成 `"梅" / "拉" / "妮"` 三个单字，在 BM25 里很难精准打分。我当时试过两个方案：
- 先把显式 `entities` 和已注册人名作为完整短语补进索引和查询前补全（用二字前缀桶 `known_phrases_by_prefix2` 做快速匹配），解决已知人名；
- 再给显式搜索补一套汉字二元组（CJK Bigram）信号，解决没提前注册过的冷门译名与复合词。

第一版实现我图省事，直接把 `"m:cjk2:梅拉"` 这种堆分配的 `String` 塞进了每条笔记的 `term_freq` 和 `bm25_postings`，查询时用临时 `HashMap` 累加得分。效果立竿见影（LoCoMo 中文检索明显涨点），但一跑 2000 条语料的微基准，两个警报同时亮了：每条中文笔记凭空多出几十个堆字符串，显式查询耗时和进程峰值内存都往上跳了一截。

第二版我把 CJK 双字彻底从主词法表剥离出来，重构成三件很轻的东西：

```rust
// 1. 两个 BMP 汉字直接打包进单个 u32，零堆分配，且跳过双停用字对
let key: u32 = ((prev_han as u32) << 16) | (cur_han as u32);

// 2. 独立紧凑倒排表：key -> Vec<(slot_u32, tf_u16)>
cjk2_postings: HashMap<u32, Vec<(u32, u16)>>,
```

查询期完全不创建 `HashMap`，而是复用线程本地的代次计数缓冲区 `Cjk2Scratch`（类似稀疏向量标记，每次查询只自增 `query_gen`，O(1) 清空），用 `select_nth_unstable_by(64, ...)` 替代全量排序；更进一步，因为只有 `recallable == true` 的笔记才会写进 `cjk2_postings`，当 `MemoryFilter` 为空（绝大多数搜索场景）时，打分阶段直接按 `slot` 读取 `slot_notes`，彻底省掉上百次主表 `HashMap<Uuid, IndexedNote>` 查找。

这一轮重构之后，显式检索均值从字符串键方案的 `159 µs` 压回 `149 µs`，进程峰值内存回落约 `1.6 MiB`，LoCoMo 中文对话视图 `explicit@3` 提升 `+1.50 pp`（`51.89% -> 53.39%`）、`explicit@5` 提升 `+1.75 pp`（`59.51% -> 61.26%`），而且自动召回与 OP-Bench 指标零波动。

## 五、端侧部署最隐蔽的炸弹：模型权重与 18 MB 分词器 JSON

检索算法调完，我以为最难的部分结束了，结果一测进程冷启动时间和峰值内存，直接被现实教做人。

Embedding 模型我们选的是 `minishlab/potion-multilingual-128M`。它本质上是一个多语种静态词表向量表（500,353 词 × 256 维），推理不需要跑 Transformer 前向，把分词结果查表做语料 IDF 加权池化再 L2 归一化就能算出质量很不错的语义向量。纯 Rust 写完推理代码不到两百行，零 Python 依赖。

但部署时马上冒出两个内存炸弹：

### 炸弹一：489 MB 的 F32 权重表

原始 `model.safetensors` 是 `489 MB` 的 `F32` 矩阵，全读进堆内存对端侧来说太奢侈。我们用纯 Rust 写了流式逐行 int8 对称量化：每行求 `max_abs / 127.0` 存一个 `f32` scale，权重压成 `i8`，落盘成一个 `124 MB` 的二进制文件 `potion-i8.cache`，文件头带 v2 魔数与头/中/尾各 4 KB 采样 SHA-256 自校验。

Unix 平台下用 `libc::mmap(PROT_READ, MAP_PRIVATE)` 叠加 `MADV_RANDOM` 只读映射进虚拟地址空间。板端部署根本不用带 489 MB 的原始 safetensors，操作系统只把实际查到的词表页按需换入内存，实测映射页 `DIRTY=0K`，真正活跃驻留的物理内存只有几十兆。

### 炸弹二：18 MB `tokenizer.json` 吃掉 666 MiB 启动峰值内存

权重改成只读 mmap 之后，我本以为整进程峰值内存会瞬间掉到几十兆。用 `/usr/bin/time -l` 一跑，结果冷启动耗时仍然要 `0.66 s`，进程峰值 RSS 居然还有近 **800 MiB**。

把权重加载注释掉单独测，才抓出真正的元凶：**18 MB 的 HuggingFace `tokenizer.json`**。

`potion-multilingual-128M` 的词表有 50 万个 Unigram 词元。调用 `tokenizers::Tokenizer::from_file` 时，库会先把 18 MB JSON 整棵反序列化成临时对象，再在堆上建各种 `String`、哈希表和 Double-Array Trie，瞬时峰值内存直接飙掉六百多兆，冷启动解析耗时 `407.70 ms`。

为了把这颗雷排掉，我写了一个不引入新第三方依赖的二进制分词缓存 `potion-tok.cache`：
1. 离线或首次启动时，用流式 `serde::de::Visitor` 单遍扫描 `tokenizer.json` 的 `vocab` 字段，不构造整棵 JSON DOM；
2. 将 500,353 个词元按排序 BFS 压缩成只读 CSR 基数树（Radix Trie），最终只有 617,406 个节点、888 KB 后缀区、完整 `f64` 得分表及 `normalizer` / `pre_tokenizer` / `added_tokens` 元数据，总文件大小仅 **12.6 MiB**；
3. 运行时同样通过 `PROT_READ | MAP_PRIVATE` + `MADV_RANDOM` 做只读 `mmap` 与采样 SHA-256 校验，直接在映射字节上跑精确 `f64` Viterbi 切分（完整支持 `fuse_unk`、`byte_fallback` 和特殊词元提取）。

效果非常干脆：在 4,339 条真实多语种评测字符串上与 HuggingFace `tokenizers` 保持 **100% 逐 token 一致**，分词器加载耗时从 **`407.70 ms` 降到 `3.34 ms`**，端侧模型包体从 `507 MB`（`489 MB` 权重 + `18 MB` JSON）压缩到 **`137 MB`**（`124 MB` 量化缓存 + `13 MB` 分词缓存），2000 条满库微基准的整进程 `peak memory footprint` 稳在 **`56.3 MiB`**。

顺带记录一个排查时差点骗过自己的版本兼容坑：如果开发机模型目录里之前残留了旧版无自校验的 `V1` 权重缓存，且目录里同时留着 `model.safetensors`，向后兼容分支会直接放行 `V1` 而不触发 `V2` 重建；一旦把缓存文件单独拷到不带 `model.safetensors` 的板端目录，加载器会拒绝无校验的 `V1` 并静默回退到离线哈希投影。因此在打包端侧产物的脚本里，必须显式校验缓存文件的魔数版本号，不能只看文件名存在。

## 六、公开基准实测与还没打穿的地方

把这套纯 Rust 单进程引擎放在 4 套公开基准和 release 微基准下跑完，核心指标汇总如下（均开启本地 `potion-multilingual-128M` 量化缓存，除微基准外均为离线预填充语料检索评测）：

| 评测基准 | 核心指标 | 实测结果 |
| --- | --- | --- |
| **LoCoMo English**（10 场对话，1536 问） | dialogue `explicit@10` / `@32` Hit | `70.51%` / `80.34%` |
| **LoCoMo Chinese**（10 场对话，1536 问） | dialogue `explicit@3` / `@5` / `@10` / `@32` Hit | `53.39%` / `61.26%` / `69.66%` / `80.79%` |
| **LoCoMo Chinese**（observations 视图） | `explicit@3` / `@10` / `@32` Hit | `54.95%` / `66.34%` / `74.28%` |
| **LongMemEval-S**（按真实时间线写入，470 正例 + 30 拒识） | `Recall@10` / `NDCG@10` / `temporal@32` | `95.38%` / `0.9036` / `95.09%` |
| **LongMemEval-S (`_abs`)** | 无答案误注入率（越低越好） | `46.67%`（门控前 `73.33%`） |
| **OP-Bench**（418 题无关个性化抑制） | Abstention Rate / False-Injection Rate | `91.15%` / `8.85%`（门控前 `18.66%`） |
| **Memora Weekly**（Track B lifecycle，150 问） | `Forget Absence@10` / `FAMA@32` | `98.63%` / `66.47%` |
| **Release 微基准**（`corpus=2000`，单机） | `auto_recall` p50 / `explicit_search` mean / Peak Footprint | `242 µs` / `149 µs` / `56.30 MiB` |
| **分词器缓存**（50 万词表，CSR Radix Trie） | 冷加载耗时 / 4339 串逐 token 一致率 | `3.34 ms`（原 `407.70 ms`）/ `100%` |

做到这里，检索精度、误注入抑制、端侧内存和百微秒级延迟基本都站稳了，但有两件事这套基准测不出来，也是我接下来最想补齐的短板：

1. **写入与巩固闭环的真实模型量化评测**。上面四套公开基准都是把语料预先灌进索引测检索，线上真实体验的另一半取决于后台小模型写得准不准。比如用户说“以前喝冰美式，最近胃不好戒咖啡了”，巩固管线能不能稳定产出否定更新、拦住闲聊脏记忆，以及三元组抽取会不会飘，不建一套端到端的真模型回放集，去盲调巩固提示词基本等于开盲盒。
2. **“用户明确说过”与“系统推断偏好”的边界治理**。参考过另一套重治理设计的记忆系统后，我觉得有两条机制很值得吸收进这套原生引擎：一是给从多次经历归纳出的软偏好建立独立状态机（`pending / usable / paused / rejected`），至少两条独立事件才允许升格，用户口头否决或暂停后锁死旧证据防止后台重跑复活；二是同轮拒存传播，在用户当轮明确说“别记住这件事”时，同步拦截紧随其后的助手复述进入后台抽取。

端侧 Agent 长期记忆其实不缺花哨的概念，难的是在内存、延迟、召回和克制之间同时守住底线。把底座做轻、把边界锁死、拿公开基准和微基准盯着每一处改动，比堆叠组件管用得多。
